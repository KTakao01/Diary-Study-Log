# 既存コードを再利用するとき、見落としていた前提条件

- 記録日：2026-11-08
- 分類：技術概念・仕組みの学習ログ

「なぜ、ユニットテストでこの問題を見つけられなかったのか」

「フォールバックは重点的にテストするように伝えたはずなのに」

そう考えているうちに、テストの前段階にある、自分のコードの読み方が気になった。

既存の処理を流用するとき、私は「今回使いたい機能が、どう動いているか」に集中していた。どの関数を呼び、何を渡し、何が返ってくるか。自分が実現したい処理につながる部分を追いかけて、使えそうだと判断する。

そこで確認が薄くなっていたのが、「この処理は、どんな条件のもとで正しく動くのか」という点だった。

たとえば、説明用の仮例として、SQSというメッセージキューへ通知を送る部品を考える。この通知は補助的な機能で、送信に失敗した場合はログを残し、呼び出し元の処理を続ける仕様になっているとする。

その前提なら、「送信失敗時にログが残り、処理を継続できる」というテストには意味がある。

ここで、この送信部品を申込受付APIに流用する。受付APIでは、申込データをキューに送信できた時点で「受付完了」と応答する設計だとする。

同じキューへの送信でも、失敗したときに求められる振る舞いが変わる。

もし送信部品がエラーを内部で処理し、呼び出し元に失敗を伝えなければ、受付APIは申込をキューに登録できていないのに「受付完了」を返してしまうかもしれない。

送信部品の単体テストは通っている。それでも、流用先で必要な条件を満たせていない。

この例で確かめたいのは、送信先がエラーを返したとき、その失敗が受付APIまで伝わり、呼び出し元にもエラーが返ることだ。送信部品と受付処理を組み合わせて、外部に返す結果まで確認する。その際、エラーを内部で処理する送信部品自体もテスト対象に含める。

「異常系をテストする」「フォールバックを重点的に見る」という指示も、もう一段具体化したい。フォールバックは、ある処理が失敗したときなどに代替処理へ切り替えることだ。その切り替えを確認するだけでなく、代替処理の結果をどう扱うかまで決める必要がある。

代替処理が成功した場合、何をもって処理完了とするのか。利用者には何を返すのか。代替処理まで失敗したら、どこにその失敗を伝えるのか。

そこまで決めることで、テストの期待結果がはっきりする。

ユースケースで利用者の目的を整理し、ロバストネス図やシーケンス図で役割や処理の流れを追うと、仕組みを理解しやすくなる。そのとき、成功条件や失敗時の分岐も書き込めば、再利用の前提を検討する助けになる。

自分の場合は、「この順番で動く」という理解で止まってしまい、「この条件が変わっても大丈夫か」という検討まで進めていなかったのだと思う。

リグレッションテストについても、同じことが言える。既存のテストを通すことは、そこで確認している振る舞いを保つうえで重要だ。そのうえで、流用先に新しい入力や実行条件、成功条件があるなら、その差分をテストに追加する必要がある。

既存コードには、まだ見つかっていない不具合が残っていることもある。また、元の用途では妥当な振る舞いが、別の用途では問題になることもある。通知用の送信部品の仮例では、元の仕様と流用先の成功条件の違いを確認することが重要だった。

今後、既存の処理を使うときには、少なくとも次の三つを言葉にしてから判断したい。

- 元の用途では、何をもって成功としているか。
- 失敗したとき、呼び出し元は何を受け取るか。
- 今回の用途でも、その振る舞いで要件を満たせるか。

コードを読み始める前に、この三つを書いておく。読み進めながら既存の振る舞いと照合し、用途によって変わる条件をテストケースに落とし込む。自分が使いたい処理を見つけた後も、呼び出し元に返る結果まで確かめたい。
