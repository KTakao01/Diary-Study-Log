# 『失敗から学ぶRDBの歩き方』読書考察：削除フラグは採用してよいのではないか

- 記録日：2026-10-17
- 元の考察：2025-12-18〜19の読書・対話
- 追記：2026-10-17時点の考え

『失敗から学ぶRDBの歩き方』を読んだ際の削除フラグについての考察を、当時の対話と今回の振り返りから再構成する。本書の文章を引用するものではなく、当時の自分の疑問・主張を記録する。

## 1. 当時の立場：要件と対策次第で、削除フラグは導入してよい

削除フラグへの批判を読んで、採用自体を避けるべきなのか疑問に思った。自分は、削除フラグを採用する理由はある、という側から考えていた。

まず、削除後も「消したデータが何だったか」を確認したい要件がある。削除したIDだけを履歴に残しても、その内容までは分からない。元の内容を保持することに意味があるなら、単に行を消すだけでは要件を満たせない。

もちろん、内容を保存する履歴テーブルでも対処できる。ここでの疑問は履歴テーブル全般への否定ではなく、「IDだけ残せば十分」としてよいのか、というものだった。何を後から確認したいかを先に決め、その要件に合う保持方法を選びたい。

次に、削除済みデータを集計などに混ぜてしまう原因が、SQLに除外条件を書き忘れることなら、有効なデータだけを返すVIEWを用意すればよいのではないかと考えた。各利用者が毎回同じ条件を書く必要を減らせるのでは、という対案である。

### 2026-10-17の振り返りで補足：状態と削除日時を持たせる案

今回の振り返りでは、当時の考察として、次の二つの対案も補足した。当時の対話にも `status` と `deleted_at` の説明がある。以下は当時の発言の逐語引用ではなく、今回の振り返りを含めた再構成である。

一つ目は、0/1や単に `deleted` とするだけでは、業務上どういう状態なのか分からないという問題への対案である。削除かどうかだけで区切るのではなく、削除以外の状態も明示的に持たせればよいのではないかと考えた。

例えば、有効・停止・終了といった状態を `status` で区別する。これは説明用の仮の例であり、必要な状態は対象の業務によって異なる。停止や終了をすべて「削除済み」に押し込めず、意味の違いをデータとして表したいという考えである。

二つ目は、0/1だけでは削除時期が分からず集計しづらいという問題への対案である。削除日時を `deleted_at` に記録すれば、未削除かどうかに加え、いつ削除したかも分かる。例えば「NULLなら未削除、日時があれば削除済み」とすれば、二値フラグの代わりになり、削除時期で絞り込んだ件数も集計できる。

削除済みを通常の集計から除外する話と、いつ削除されたかを集計する話は別である。前者への対案がVIEW、後者への対案が削除日時の記録だった、という整理になる。

今回の整理では、それぞれの役割を次のように分ける。

| 持たせるもの | 表現・対処したいこと |
| --- | --- |
| `status` | 業務上の状態の違い |
| `deleted_at` | 論理削除の有無と削除した時点 |
| 有効なデータを返すVIEW | 通常の読み取りで削除済みを除外する条件の集約 |

つまり、単純な0/1フラグですべてを表そうとすることの限界に対して、必要な情報を追加・分離すれば、論理削除を採用できるのではないかという考察である。

当時の主張は、「削除フラグに欠点があること」と「削除フラグを採用すべきでないこと」は別ではないか、というものだった。履歴保持の要件があり、利用時の問題にも対策を取れるなら、導入してよいと考えていた。

## 2. 2026-10-17追記：個人情報については、物理削除を優先すべきかもしれない

最近は情報漏えいの話題が気になっている。その観点を加えると、個人情報については「物理削除が正義」かもしれない、とも思うようになった。

削除フラグを付けたり、VIEWから見えなくしたりしても、元のテーブルには内容が残る。通常の検索結果に出さないことと、保持する情報自体を減らすことは違う。

当時は「後から確認できること」の利点を重視していた。今は、その便利さのために、使わなくなった個人情報まで残し続けてよいのかも考えたい。

現時点では、保持する必要がなくなった個人情報は、論理削除のまま残すより、物理削除を優先する方がよいのではないか、という考えである。一方で、保持が必要な情報まで無条件に消せばよいとは考えていない。何のために、どの項目を、いつまで保持する必要があるかを区別したい。

これは当時の主張を全面的に撤回するものではなく、削除方法を選ぶ際に、履歴を残す利点だけでなく、残した情報が漏れる場合の影響も考慮したいという追記である。

## 3. 原稿化時の補足：VIEWと物理削除、それぞれの限界

以下は今回の原稿化にあたって加えた整理であり、当時の対話で検証済みだった結論ではない。

- **VIEWは除外条件をまとめる手段。** それを経由する読み取りでは条件の書き忘れを減らせるが、元のテーブルを直接読む経路には効かない。利用経路と権限の設計が必要で、VIEWを作るだけで漏えい対策が完了するわけではない。[1]
- **削除日時1つで、すべての履歴を表せるわけではない。** 復元時に `deleted_at` をNULLへ戻し、再削除時に上書きする設計では、以前の削除日時は失われる。削除イベントの全件集計や過去時点の業務状態を再現したいなら、別途履歴が必要になる。また、物理削除すればその行の `deleted_at` も消えるため、この日時による集計は行を保持している範囲に限られる。
- **履歴テーブルへの移動も、情報の保持である。** 個人情報を履歴側にそのまま残すなら、現在のテーブルから消しただけでは、保持する情報を減らしたことにはならない。
- **ここでいう物理削除は、主にDBの行をDELETEする意味。** 記憶媒体上のデータを直ちに復元不能にする処理と同義ではない。例えばPostgreSQLでは、DELETE後も古い行バージョンが直ちに除去されるわけではない。[2]
- **現在のDBから削除しても、別のコピーは別途考える必要がある。** 削除前のバックアップから復元すれば、その時点のデータが戻り得る。[3] ログ・キャッシュ・連携先にもコピーがある設計なら、それぞれの保持期間や削除・復元時の扱いを検討したい。

## 4. 現時点の整理

削除フラグを採用すること自体は、今も一律に否定しない。ただし、「あとで使うかもしれない」という理由だけで個人情報を残し続けることには慎重になった。

履歴として必要な情報と、もう保持する必要のない個人情報を分け、後者は物理削除を優先する。そのうえで、削除対象が現在のテーブルだけでよいのかまで考える、というのが今の暫定的な整理である。
