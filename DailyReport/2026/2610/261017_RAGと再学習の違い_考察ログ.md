# RAGで「再学習しない」と「再学習できない」は同じなのか

- 記録・整理日：2026-10-17
- 元のやり取り：2025-09-15〜16
- 分類：技術概念・仕組みの学習ログ

過去の対話から、自分の疑問と考えたことを再構成した記録。発言の逐語引用ではない。特定のサービスの契約や現行ポリシーを評価する記事ではなく、推論・学習・データの扱いを区別するための考察を記す。

## 1. 当時どう考えていたか

RAGで情報を参照させることと、LLMをその情報で学習させることは、どう違うのかを確認していた。

その説明を聞いても、データを読み取れる側が、そのデータを保存して別の学習処理に使うことは技術的には可能なのではないか、と疑問が残った。

再学習に使わないという約束や運用と、仕組み上どうしても再学習できないことは、同じではないはずだ。ネットワークを閉じることについても、それだけで学習処理を実行できなくなるのか、と問い直していた。

渡す情報が断片的だったとしても、蓄積して学習用に整える可能性までなくなるわけではないのではないか。この問いは、特定の提供元が実際にそうしていると主張するものではなく、説明の根拠を確かめるものだった。

## 2. 原稿化時の補足：推論に使う処理と、重みを更新する処理

以下は今回加えた整理であり、当時すべてを検証済みだったという意味ではない。

生成モデルの重みを固定したRAGの推論では、質問に関係する情報を検索し、その情報を使って回答を生成する。その回答に情報が反映されること自体は、生成モデルの重みを更新したことを意味しない。

一方、ファインチューニングは、事前学習済みのモデルをデータセットでさらに学習させる工程である。[1] 推論に入力したことと、そのデータで追加学習を実行したことは分けて扱う必要がある。

ただし、「RAGなら学習工程が一切ない」とまで言うと不正確になる。RAGの原論文にも、検索と生成を組み合わせたモデルをファインチューニングする記述がある。[2] ここで区別したいのは、検索結果を回答に使う今回の推論と、モデルを更新する学習工程である。

## 3. 仮例：架空のボードゲームのルールを回答に使う

以下は公開用に新しく作った説明用の仮例。ルール文や手順は、実際の業務資料・データ・コードからの転記ではない。

架空のゲームのルール集に「開始時に各プレイヤーへ青いコマを三つ渡す」と書かれているとする。

1. 「最初に配るコマはいくつか」という質問を受け取る。
2. ルール集から関連する文を検索する。
3. 質問と検索した文を、重みを固定した生成モデルへ渡す。
4. モデルが、その入力を使って回答する。

この処理に重みを更新する工程はない。しかし、ルール文やリクエストのログを保存するかどうかまでは、この四つの手順だけでは分からない。仮に保存されたデータを別の学習工程へ渡せる構成なら、その利用可能性は別途検討することになる。

また、ルール集を検索用の索引へ登録することも、生成モデルの重みを更新することとは別の処理である。保存先や検索方法を変えることと、生成モデルの追加学習を混同しないようにしたい。

## 4. 「しない」の根拠を分けて考える

当時の問いを踏まえると、次の説明はそれぞれ確認している対象が異なる。

| 説明 | 確認している対象 |
| --- | --- |
| この推論処理では重みを更新しない | 実行する処理の内容 |
| 入力を学習用途に使わない方針である | データの利用方針・約束 |
| 学習環境から入力データへアクセスできない | 指定した環境・権限でのアクセス制限 |
| 入力を保存しない設計である | 保存先・ログを含めたデータの保持方法 |

ある一つが成り立つことから、残りすべてを自動的に導くことはできない。技術的な制限についても、誰がどの権限を持つ前提なのかを含めて確認する必要がある。

この表は今回の原稿化で加えた整理であり、特定の製品の保証内容や契約解釈を示すものではない。

## 5. 今回の整理と、追加で検討する論点

当時問い直したかったのは、RAGの仕組みだけを根拠として、渡した情報の将来の利用方法まで断定できるのか、ということだった。

今回の整理では、「回答時に参照する」「保存する」「学習に利用する」を別の処理として追うことで、何が説明され、何がまだ説明されていないかを確かめられる。

追加の検討点は、入力・検索結果・ログの保存範囲、保存先へのアクセス権、学習環境へのデータ経路、設定変更を確認する方法である。これらは今後確認するための論点であり、具体的なサービスで確認済みだったとは扱わない。
