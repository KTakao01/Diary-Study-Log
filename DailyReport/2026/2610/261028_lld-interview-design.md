# LLD面接では、すべての図を描く必要があるのか

記録日：2026-10-28

## 疑問と結論

ユースケース、ドメインモデル、ロバストネス図、クラス図、シーケンス図を限られた面接時間ですべて作るのは難しい。

**本書の開発プロセスを面接で全部再現する必要はない。要件から責務・関係・処理の流れを説明するために、必要な成果物へ絞る。** ここではLLD（低レベル設計）の面接を想定する。面接官の指定がある場合は、その課題と成果物を優先する。

| 検討すること | 限られた時間での表現方法 |
| --- | --- |
| ユースケース | 主な操作、前提、成功・失敗時の結果を短い箇条書きで確認 |
| ドメインモデル | 主要な概念を見つけ、そのままクラス図の出発点にする |
| ロバストネス分析 | 誰が入力を受け、誰が処理し、何を更新するかを検討。独立した図は必要に応じて省略 |
| クラス設計 | 主なクラス・責務・関係・必要な操作を図にまとめる |
| シーケンス | 複雑な処理だけ図にする。単純な処理はクラス図と口頭説明でたどる |

## 一つの設計を育てる

説明用の書店なら、「本を探す・カートに入れる・注文する」を確認し、Book・Cart・Orderなどを置く。「注文する」をたどり、在庫不足や支払い失敗も検討しながら、必要なメソッドや調整役を追加する。

段階ごとに別の図を清書する代わりに、一つの設計を更新する。ドメインの概念と技術的な役割の違いは意識するが、必ず別々の成果物を作る必要はない。

**図を省くことと、検討を省くことは別。** クラス名・メソッド名を列挙するだけでなく、具体的なユースケースを実行できるか、例外時にどうなるかを説明する。コード実装も課題なら、作図をさらに絞って実装時間を確保する。

進め方の説明例：「主要なユースケースを確認してクラス構成を描き、複雑な処理だけシーケンスで補足します。」
