# 『現場で役立つシステム設計の原則』のNOT NULL・正規化方針を原文で確認する

記録日：2026-10-29

「すべてのカラムをNOT NULLにする」「一意性制約とNOT NULL制約で自然に正規化される」という理解が、実際の本の記述と合っているかを確認した。どちらにも原文の根拠があった。ただし、著者はテーブル分割による結合の複雑化や性能問題も認識し、対策を説明している。

残すべき疑問は、**任意項目まで一律に別テーブルへ分ける必要があるのか、制約を手がかりにするだけで正規化の判断を十分に説明できるのか**、という点になる。

## 原文で確認できたこと

| 確認したかった主張 | 判定 | 根拠 |

| 入力が任意の項目は別テーブルにするのか | 原文にある | PDF pp.121–122 |

### 1. NOT NULLの徹底と任意項目の分割

第6章「NOT NULL制約が導くテーブル設計」、PDF p.121：

> カラムはすべて NOT NULL 制約にします。そして、もし NULL 値がどうしても必要なカラムを見つけたら、別のテーブルに分けることを検討します。この方法を徹底するだけで、テーブルの正規化が進みます。

同節の続き、PDF p.122：

> 入力が必須ではない項目は、別テーブルになるということです。それがデータを正しく記録する方法です。

したがって、「必須項目にはNOT NULLを使おう」という限定的な助言よりも強い方針が書かれている、という読みは妥当だと思う。一方、PDF p.121では、値がない場合に `unknown` や `9999` を埋める「NULL逃れ」も否定している。欠損を適当な値で隠すことを勧めているわけではない。

### 2. 制約と正規化の関係

第6章「外部キー制約でテーブル間の関係を明確にする」、PDF p.122：

> 既存のテーブル設計を改善するために、一意性制約と NOT NULL 制約を追加してみることが有効です。テーブルも自然に正規化されます。

ただし、同じPDF p.122の「一意性制約でデータの重複を防ぐ」では、次のようにも書かれている。

> しかし、一意性制約は、主キーを決めればよい、という話ではありません。

前後を含めた要約としては、カラムの組み合わせが何を一意にするかを考え、重複して記録している事実を見直し、必要に応じて分割するという設計の進め方である。分割後の関係を外部キー制約で保証することにも触れている。

このため「主キーとNOT NULLさえ付ければ自動的に正規化が完了する、とだけ書いている」と要約すると不正確になる。一方で、「自然に正規化されます」という言い切りから、どの依存関係を確認すればよいかが分かりにくい、という疑問は残る。

### 3. 結合の複雑化と性能問題

第6章「参照をわかりやすくする工夫」内「コトの記録に注力したテーブル設計の問題」、PDF p.126：

> しかし、NOT NULL 制約を徹底した場合は、カラム数の少ないテーブルがたくさん生まれます。必要な情報を取り出すために、多くのテーブルを結合する複雑さが生まれます。

同ページの「状態の参照」では、対策として次の方針も示されている。

> 導出の性能を考慮して、コトの記録のたびに状態を更新するテーブルも用意する

本文の要約：出来事の記録を基本とし、現在の状態を高速に参照するためのテーブルを別に持つ。その状態テーブルは、元の記録から再構築できる派生データとして扱う。

「分割したら結合が増えるのでは」という疑問は、本自身も認めている。一方、著者が性能を無視しているとまでは言えない。

## 自分の批判と疑問

### 制約を付けることと、正規化を判断することは別ではないか

NOT NULLは値の欠損を禁止し、UNIQUEは指定した列の組み合わせの重複を禁止する。これらは重要だが、それだけで、別の列がどの事実に依存しているかを判断してくれるわけではない（[PostgreSQLの制約の説明](https://www.postgresql.org/docs/current/ddl-constraints.html)）。

以下は説明用の架空の例。顧客は複数の注文を持てるが、現在の顧客名は顧客IDごとに一つに決まるものとする。

```sql
CREATE TABLE orders (
    order_id INTEGER NOT NULL PRIMARY KEY,
    order_number TEXT NOT NULL UNIQUE,
    customer_id INTEGER NOT NULL,
    current_customer_name TEXT NOT NULL
);
```

| order_id | order_number | customer_id | current_customer_name |
| --- | --- | --- | --- |
| 101 | ORD101 | 7 | 顧客A |
| 102 | ORD102 | 7 | 顧客A |

すべてのカラムがNOT NULLで、候補キーである注文IDと注文番号にも一意性の制約がある。それでも、業務上は `customer_id → current_customer_name` という依存関係があるため、同じ顧客の現在名を複数行に記録している。

片方の行だけを「顧客B」に更新しても、上の制約には違反しない。顧客名の不整合を許してしまう。注文を一意に決められない顧客IDから、候補キーに含まれない現在名が決まっており、この設計は第3正規形を満たさない。顧客IDをキーとする顧客テーブルへ現在名を分ける判断が必要になる（[Cornell Universityの第3正規形の説明](https://cvw.cac.cornell.edu/RelationalDBs/design-create/third_normal_form)）。

ここで `customer_id` をUNIQUEにしてしまうと、同じ顧客が複数回注文できなくなる。任意の列に一意性制約を追加すればよいわけでもない。

なお、これは「現在の顧客名」を重複保持する例。「注文時点の宛名を履歴として保存する」という要件なら、保存する事実が異なるので同じ批判はできない。

本の助言を、依存関係に気づくための実践的な入口として読むことはできる。ただ、自分としては、**何が何を一意に決めるのかを先に理解したほうが、分割の理由を説明しやすい**。制約の追加だけを第3正規形などの十分条件として受け取るのは誤りになる。

### 任意項目という理由だけで、必ず別テーブルにする必要があるのか

たとえば、ユーザーが任意で登録する一つのプロフィールメモを考える。これも架空の例である。

| 設計 | メモ未登録の表現 | メモも含めた一覧取得 |
| --- | --- | --- |
| `users` にNULL可能な `profile_note` を置く | `profile_note IS NULL` | 一つのテーブルから取得 |
| `user_profile_notes` にNOT NULLな `note` を置く | 対応する行が存在しない | `LEFT JOIN` などで取得 |

後者では、`user_profile_notes.user_id` を主キーかつ `users.user_id` への外部キーにすれば、ユーザーごとにメモを0件または1件持つ関係を表せる。登録済みのメモには必ず値がある、という制約も明確になる。

ただし、未登録ユーザーも含めた一覧を外部結合で取得すれば、そのユーザーの `note` は結果上NULLになる。保存する列からNULLを排除しても、取得結果やアプリケーションで「値がない場合」を扱う必要まで消えるわけではない（[PostgreSQLのLEFT OUTER JOINの説明](https://www.postgresql.org/docs/current/queries-table-expressions.html)）。これは格納時の制約と結果の性質の区別であり、本が「取得結果にもNULLは出ない」と主張しているという意味ではない。

自分が比較したいのは、分割によって得られる制約や変更のしやすさと、増えるテーブル・結合・更新処理の負担である。別の更新周期を持つ、複数件に増える、独立した事実を表す、といった理由があれば分割には納得できる。一つの任意属性だけでも同じ方針を必須にする根拠は、もう少し知りたい。

NULL可能な列を選ぶ場合にも、NULLを何の意味に使うかは決める必要がある。「未入力」「未確認」「該当しない」を区別する要件があれば、一つのNULLや単なる行の不在だけでは十分ではない。

### 性能への疑問は、断定を避けて残す

当初の疑問は、任意項目を別テーブルに分け続けると外部結合の多いGET処理になり、遅くなるのではないか、というものだった。

この懸念自体は検討に値する。ただし、外部結合があることだけで性能の良し悪しは決まらない。件数、インデックス、絞り込み条件、結合で増える行数などを踏まえ、実際のクエリの実行計画や計測結果で判断したい（[PostgreSQLのEXPLAINの説明](https://www.postgresql.org/docs/current/using-explain.html)）。この記録では性能測定をしていない。

本が示す状態参照用テーブルは、読み取りを速くするための一つの対策になる。その分、元データとの整合性、更新処理、再構築の方法も考える必要がある。

そこで、批判は次の問いに修正する。

**単純な任意項目にまで分割を徹底し、その後で参照用テーブルを維持する複雑さを引き受ける価値が、どの要件のときに生まれるのか。NULL可能な列を採用する案と比較する基準は何か。**

これは「必ず遅くなる」という断定とは区別して残しておく。

## これまでの設計の議論につながること

ここからは本の主張の引用ではなく、自分の設計方針についての考察。

複雑な業務ルールが少ないなら、Goに限らず、手続き的なユースケース処理と、小さな関数・モジュールで十分な場合がある。ただし、その場合も入力処理、業務上の判断、永続化などの責務は整理する。

「責務を分ける」「業務の関心ごとにモジュールをまとめる」「状態遷移や不変条件をドメインモデルで表現する」は、同じ話ではない。関連する処理をモジュールにまとめることはできるし、すべてを複雑なドメインオブジェクトや多数の層へ分解する必要はない。

DB設計でも、表す事実や依存関係は考える。その上で、分割や追加の仕組みは、守りたいルールと変更・運用の負担を比較して選びたい。単純なドメインだから正規化が不要になるわけでも、責務を分けるために常に同じ設計様式が必要になるわけでもない。

本から取り入れたいのは、制約でデータの正しさを守ることと、重複した事実を見直す姿勢。保留するのは、すべての任意項目に同じ分割方針を適用することと、制約の徹底から正規化が自然に得られるとする説明の強さである。
