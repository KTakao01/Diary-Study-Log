# AI時代にシーケンス図をどう設計し、何を自分で判断するか

- 記録日：2026-10-27
- 分類：技術書の読書・設計の考察ログ
- 読書対象：『ユースケース駆動開発実践ガイド』第8章、Kindle版 p.220

『ユースケース駆動開発実践ガイド』は、ユースケースから設計を具体化する流れが分かりやすいと感じている。一方で、AIを使って開発する場面を考えると、知らないアーキテクチャや関数・クラスの構成を把握して、最初から自分でシーケンス図を描けるだろうか、という疑問が生まれた。

同日の[フロントとバックエンドの設計図に関する記事](261027_バックエンドのロバストネス図とシーケンス図_読書考察ログ.md)とは分けて、今回は「AIと人間で、図の作成と設計判断をどう分担するか」を記録する。以下は読書と対話をもとに整理した考察と今後の方針であり、実際のアプリを実装・検証した結果ではない。

## 1. 着想の起点：メッセージを描いて、操作の担当を決める

- **書籍**：『ユースケース駆動開発実践ガイド』
- **著者**：ダグ・ローゼンバーグ、マット・ステファン
- **該当箇所**：第8章「4. メッセージを描くことによって、操作をクラスに割り当てなさい」
- **ページ番号**：Kindle版 p.220。PDFファイル上のページ番号やKindleの位置番号ではない。

> クラスへの操作の割り当てをシーケンス図によって行うことは重要です。ですから、メッセージを描くときには2番目の方法を使うべきです。

ここでいう「2番目の方法」は、UML作図ツールで矢印の先頭部分を操作し、ターゲットとなるクラスに操作を直接追加する方法を指す。

この説明から、シーケンス図を描くことは、処理順を絵にするだけでなく、「この処理をどのクラスに担当させるか」を決める作業でもあると理解した。

そこから、次の疑問につながった。

> 見知らぬアーキテクチャや関数群・クラス群を使う場合、自分でシーケンス図を作れる気がしない。AIに書いてもらい、その内容を判断することになるのだろうか。

この疑問と、以下のAIを使った進め方は、自分の読書上の考察であり、書籍の主張をそのまま引用したものではない。

## 2. 既存コードを調べる場合と、新規設計の場合を分ける

まず、同じシーケンス図でも、何を根拠に描くのかが異なる。

| 対象 | AIに手伝ってもらうこと | 図の位置付け | 判断するときの根拠 |
| --- | --- | --- | --- |
| 既存システム | 関連コードを調べ、呼び出しやデータの流れを図にする | 現在の実装を説明する図 | コード、設定、仕様、テストや実行結果 |
| 新しく作る機能 | ユースケースをもとに、処理の担当とやり取りを提案する | これから実装する設計案 | 要求、制約、既存の技術構成、失敗時の扱い |

既存システムでは、実際にどの関数が呼ばれるかを調べられる。ただし、AIが関連するコードや設定にアクセスできることが前提になる。確認できない部分を想像で補った図は、実装を確認した証拠にはならない。

新規設計には、まだ実装上の答えがない。AIが出すクラス名や呼び出し順は候補として扱い、なぜその分担にするのかを検討する。既存の構成へ機能を追加するなら、その構成や制約も判断材料になる。

また、実装に忠実な図であっても、利用者の要求を満たしているとは限らない。「コードどおりか」と「仕様として妥当か」は分けて確かめる必要がある。

## 3. 既存システムでは、図と根拠をセットで読む

説明用の例として、「書籍詳細を表示する」機能を考える。まず、対象を次の範囲に絞る。

- 利用者が書籍を選ぶと、詳細が表示される。
- 対象の書籍が見つからない場合は、その旨が表示される。

このユースケースに関係する入口から応答までをAIに調べてもらい、主な矢印に対応するファイルや行を示してもらう。すべてのクラスを先に覚えるのではなく、ひとつの利用者の操作に関係する経路を追う。

例えば、図に `BookDetailsController` から `BookDAO.findById(bookId)` への矢印があれば、次を確認する。クラス名は書店の説明用の例であり、実際の調査ではそのリポジトリに存在する名前を使う。

| 確認したいこと | 調べる内容 |
| --- | --- |
| 本当に呼んでいるか | 呼び出し元のコードと、呼び出し先の定義が対応しているか |
| 何を受け渡すか | 書籍ID、戻り値、見つからない場合の表現は何か |
| 処理が抜けていないか | 認証、入力検証、例外処理など、前後にある処理を省略していないか |
| 実行時に変わる部分はあるか | DIの設定や条件分岐によって、実際の呼び出し先が変わらないか |
| 何を確認できたか | コード上の確認、テスト結果、未確認の部分が区別されているか |

ファイル名や行番号が付いていても、それだけで図が正しいとは決めない。重要な矢印は実際に該当箇所を開き、AIの説明と照らし合わせる。必要に応じてテストや実行時の記録も使う。

特に、データの更新、外部サービスへの依頼、失敗時の分岐は優先して確認したい。テストが成功していても、そのテストが確認していない条件まで正しいと判断することはできない。

## 4. 新規設計では、業務ルールと失敗時の扱いから詰める

新しく「書籍を注文する」機能を作る場合、最初から全メソッド名を決める必要はない。まず、利用者が何を達成したいのかと、そのための条件を整理する。

例えば、説明用の業務ルールとして「支払いに失敗したら注文を確定しない」を置く。そのうえで、AIにController、Service、DAOなどの責任分担を提案してもらう。

提案を判断するときには、次のように問いを具体化する。

- 支払いの成功は、どこで確認するのか。
- 支払い成功後に注文の保存が失敗したら、どの状態が残るのか。
- 同じ依頼が再送されたら、二重に処理されないか。
- 各処理をそのクラスに置く理由は何か。

ここでは、図がきれいに描かれているかよりも、利用者の目的とシステムに残る状態が整合しているかを確かめる。

Controller・Service・DAOという構成は一例であり、どのシステムにも一律に当てはめるものではない。使う技術の実行モデルや責務が分からず判断できない部分は、資料を調べたり、小さく動かして確認したりして、判断できる範囲まで具体化する。

## 5. AIへの依頼も、検証できる形にする

既存コードを調査するときは、次のように依頼したい。

```text
対象は、既存の「書籍詳細を取得する」処理です。
まずコードを変更せずに調査してください。

1. リクエストの入口から、データ取得、応答までを追ってください。
2. 正常時と書籍が見つからない場合のシーケンス図を描いてください。
3. 主な矢印について、根拠となるファイルと行を示してください。
4. コードから確認できたこと、推測、未確認のことを分けてください。
5. 関連するテストと、図やテストで確認できていない点を挙げてください。
6. 実装上の振る舞いと、要求される振る舞いに違いがあれば示してください。
   要求が分からない部分は、仕様上の正しさを断定しないでください。

コードや設定を確認できない部分は、想像で確定しないでください。
テストを実行した場合は、コマンドと結果を示し、未実行なら明記してください。
```

Claude Codeの公式ガイドでも、確認用のテストなどを与え、実行したコマンドと出力などの証拠を求めることが勧められている。[1] 上の依頼文は、その考え方をシーケンス図の調査に当てはめた自分用の例である。

## 6. 今後の学び方

AIに図の作成と検証の補助を任せることはできる。ただし、「自分で描かなくてもよい」から「仕組みを理解しなくても判断できる」へ飛躍しないようにしたい。

まずはひとつのユースケースを対象に、次の順で取り組む。

1. 利用者の目的、正常時の結果、主要な失敗条件を自分の言葉で整理する。
2. AIに、その範囲の図と根拠を作成してもらう。
3. 分からない矢印を選び、対応する処理とデータを確認する。
4. 仕様との違いや未確認事項を整理し、必要な確認を進める。
5. 主要な責務と重要な失敗経路を、自分の言葉で説明できるか確かめる。

本書を読む価値は、シーケンス図を自力で記述する力に加え、図を使って何を問い、どの処理を誰に担当させるかを考えられることにもあると感じた。AIが用意した図を、その判断と学習の材料として使っていきたい。
