# スタブ・スパイ・モックの定義はどう対応するか――書籍とブログの用語を比較する

記録日：2026-10-30  
分類：読書・技術概念の学習ログ

『フロントエンド開発のためのテスト入門』と、ブログ「千里霧中」のテストダブルの説明を読み比べた。「スタブとモックの違いが資料によって違うように見える。両方が正しいなら、どう対応づければよいのか」という疑問を整理する。

現時点の理解は、**スタブとスパイの役割はほぼ対応しており、大きな違いは「モック」という語の範囲にある**というもの。本書の広い意味のモックと、ブログの分類上のMock Objectを同じ意味で読むと混乱する。

比較の鍵になる原文を、短い語句として抜粋する。

| 記事の見出し | 原文の短い抜粋 | 今回の読み取り・要約 |
| --- | --- | --- |
| Test Stub | 「間接入力を操作するTest Double」 | 依存先からテスト対象へ渡る情報を制御する |
| Test Spy | 「間接出力を記録」 | テスト対象が依存先へ渡した情報を保存し、テストコードから参照できるようにする |
| Mock Object | 「間接出力の検証能力」 | 期待を持たせた代役側で、実際の呼び出しとの一致を判定する |

このブログの区分では、スパイと狭義のモックはともに依存先への呼び出しの検証を支える。違いは、記録を後からテストコードが調べるのか、代役側が期待と照合するのかにある。入力の制御機能を併せ持つこともあるため、機能は排他的ではない。

## 3. 当初の疑問と、整理し直した分類軸

最初は「ブログは検証する状態や経路、本書は検証内容で区別している」と受け取った。しかし、読み直すと次の三つを分けたほうが正確だった。

| 観点 | 確認する問い |
| --- | --- |
| 代役の役割 | テスト対象への入力を用意するのか、テスト対象からの出力を記録するのか |
| 検証の仕組み | 記録をテストコードが検証するのか、期待を設定した代役側が照合するのか |
| テストの合否条件 | 最終結果・状態を確かめたいのか、依存先への呼び出しを確かめたいのか |

「スタブ＝状態を検証する物」と覚えると、役割と検証方式が混ざる。スタブは入力条件を作る。状態や結果を確かめるアサーションは、その条件で動かしたテスト対象に対して別に書く。

また、呼び出しを検証していても、プログラムの実行経路全体を検証しているとは限らない。指定した依存先とのやり取りを観測している。

## 4. 書籍とブログの対応表

| 実際の役割・意味 | 本書の用語 | ブログの用語 |
| --- | --- | --- |
| 依存先の返答を用意する | スタブ | Test Stub |
| 呼び出しを記録し、後からテストコードが検証する | スパイ | Test Spy |
| 期待する呼び出しを事前設定し、代役側が照合する | 今回の抜粋では独立した分類として説明していない | Mock Object（狭義のモック） |
| テスト用の代役全般を指す | モック／テストダブルという広い用法 | Test Double |
| 入力供給と呼び出し記録を兼ねる | 本書の方針ではモックと記す | スタブ機能を備えたスパイなど。兼用だけではMock Objectと決まらない |

両方の説明は、それぞれが明示した用語の範囲で読めば両立する。ただし、同じ「モック」という名前が同じ分類を指しているわけではない。

## 5. 同じJestコードで役割を対応づける

以下は理解のために作成した架空の例。書籍・ブログからの転載ではない。`api`は同期でユーザーデータを返す依存インターフェースとして扱う。

```javascript
import { expect, jest, test } from "@jest/globals";

function greeting(api) {
  const user = api.getUser(1);
  return `${user.name}さん、こんにちは`;
}

test("取得した名前で挨拶し、対象IDを依存先に渡す", () => {
  const api = {
    getUser: jest.fn().mockReturnValue({ name: "太郎" }),
  };

  const result = greeting(api);

  // テスト対象が直接返した結果の検証
  expect(result).toBe("太郎さん、こんにちは");

  // 依存先への呼び出し記録の検証
  expect(api.getUser).toHaveBeenCalledWith(1);
});
```

| コード・データ | 観点 | 役割 |
| --- | --- | --- |
| `mockReturnValue({ name: "太郎" })` | 依存先からテスト対象への返答を用意する | スタブ |
| `{ name: "太郎" }` | `getUser`の戻り値だが、`greeting`から見ると入力 | 間接入力 |
| `getUser(1)`の呼び出しと引数`1` | `greeting`から依存先への働きかけ | 間接出力 |
| `toHaveBeenCalledWith(1)` | 記録済みの呼び出しを実行後に調べる | スパイを利用した検証 |
| `result` | `greeting`が呼び出し元へ直接返す値 | 直接出力 |

「戻り値」という言葉だけでは入力・出力を区別できない。**どの関数をテスト対象としているか**で向きが変わる。

Jestの公式ドキュメントでは、モック関数は呼び出しの記録と戻り値の設定を両方提供している。したがって、APIの名前が`jest.fn()`や`mockReturnValue()`であることと、そのテストでスタブ・スパイのどちらの役割として使うかは別問題である。[1]

この例は、期待する呼び出しを代役へ事前登録する方式ではなく、実行後にテストコードで記録を検証する方式。ブログの分類に照らすと、スタブ機能を備えたスパイとして説明できる。

## 6. 読み比べて得た判断基準

資料やレビューで「モック」という言葉を見たら、次を確認する。

1. 代役全般を指しているのか、Mock Objectという限定した分類なのか。
2. 依存先の返答を変えたいのか、依存先への呼び出しを確かめたいのか。
3. 呼び出しの期待を事前設定するのか、記録を実行後に検証するのか。

自分が説明するときも「APIをモックした」で終えず、「依存先の返答を固定した」「呼び出し引数を検証した」まで書けば、流儀が違っても意図を共有しやすい。

状態の検証と相互作用の検証という整理は、Fowlerの説明とも関連する。ただし、それをスタブとモックの一対一の対応表として使うのは粗い。スパイによる呼び出しの検証もあるため、役割・検証方式・ツール名を分けて読む。[2]
