# APIを抽象化しても、固有機能は使えるのではないか

- 記録・整理日：2026-10-17
- 元のやり取り：2026-10-15
- 分類：技術概念・仕組みの学習ログ

過去の対話から、自分の疑問と考えたことを再構成した記録。発言の逐語引用ではない。「原稿化時の補足」以降は今回加えた説明・仮例であり、当時すべてを理解・検証済みだったという意味ではない。

## 1. 当時どう考えていたか

複数の外部APIを個別に扱うと処理が重複する、という説明について、何が重複するのかを確認していた。

続いて、共通化すると各APIの固有機能を使いづらくなる、という説明に疑問を持った。抽象化したとしても、元のサービスに機能があるなら呼び出せるのではないか。抽象化によって機能そのものが消えるわけではないはずだ、と考えた。

ここで曖昧だったのは、「使える」という言葉の範囲だった。システム全体として呼べることと、共通の呼び出し口だけを知る処理から呼べることは、同じなのか。

## 2. 原稿化時の補足：共通の呼び出し口が約束する範囲

抽象化では、呼び出し側が必要とする操作をインターフェースとして定められる。すべての提供元の全機能を、その一つのインターフェースに含める必要はない。

共通の型に含めなかった機能は、その型だけを受け取るコードからは、そのまま呼び出せない。一方で、固有機能を表す別の型や拡張した型を用意すれば、その機能を必要とする処理に渡せる。TypeScriptでは、インターフェースを拡張して追加の操作を表現できる。[1]

したがって、当時の「機能は使えるのでは」という指摘は成り立つ。追加で考える必要があるのは、どの呼び出し側が、どの機能や提供元を知る設計にするかである。

## 3. 仮例：静止画の変換と、アニメーションの変換

以下は公開用に新しく作った、架空の画像変換APIを扱うTypeScriptの例。実在するAPIや業務コードからの転記ではない。通信処理は省き、呼び出し口の違いだけを示す。

```typescript
interface ImageConverter {
  convert(image: Uint8Array): Promise<Uint8Array>;
}

interface AnimatedImageConverter extends ImageConverter {
  convertAnimation(frames: Uint8Array[]): Promise<Uint8Array>;
}

function convertStillImage(
  converter: ImageConverter,
  image: Uint8Array,
) {
  return converter.convert(image);
}

function convertAnimatedImage(
  converter: AnimatedImageConverter,
  frames: Uint8Array[],
) {
  return converter.convertAnimation(frames);
}
```

静止画だけを扱う処理は `ImageConverter` の操作だけを知っていればよい。アニメーションが必要な処理は、その機能を持つことを型で要求する。

これなら固有機能を使える。ただし、静止画しか変換できない実装をアニメーション用の処理にそのまま差し替えることはできない。型を用意するだけで、提供元の機能差がなくなるわけではない。

## 4. 共通化する処理も、目的に合わせて分ける

今回の仮例では、入力の前処理や変換結果の保存など、共通にできる処理を考えられる。一方、対応形式やエラーの意味などが異なるなら、その違いを扱う部分が必要になる。

共通化を「各APIの全機能を同じ操作に押し込むこと」と捉えると無理が出る。必要な操作ごとに境界を決めれば、重複を減らすことと、固有機能を使うことを両立させる余地がある。

この整理は、特定の実装方式を当時採用したという記録ではない。抽象化の利点・欠点を、どの範囲のコードについて述べているのか明確にするための補足である。

## 5. 追加で検討する論点

- どの処理には提供元を差し替えられることが必要で、どの処理には固有機能が必要なのか。
- 同じ操作名でも、入力条件やエラーの意味が違う場合、どこまで共通の契約にできるのか。
- 共通のインターフェースに追加する機能と、別の機能として分けるものを、何を根拠に判断するのか。

これらは今回の原稿化で加えた検討点であり、当時合意済みの結論ではない。
