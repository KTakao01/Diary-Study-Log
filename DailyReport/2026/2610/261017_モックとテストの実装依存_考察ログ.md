# モックを使うと、なぜ実装に依存したテストになるのか

- 記録・整理日：2026-10-17
- 元のやり取り：2026-10-13
- 分類：技術概念・仕組みの学習ログ

過去の対話から、自分の疑問と考えたことを再構成した記録。発言の逐語引用ではない。「原稿化時の補足」以降は今回加えた説明・仮例であり、当時すべてを理解・検証済みだったという意味ではない。

## 1. 当時どう考えていたか

モックを使いすぎると、テストが実装詳細に依存して壊れやすくなる、という説明に引っかかった。本物の関数を呼ぶテストも、その関数の実装に依存して動いている。それなのに、なぜモックを使う場合だけが問題になるのか。

言葉だけでは違いをつかめず、コードを並べて比較するように求めた。また、IDでデータを取得するようなDB処理では、テストデータの準備が面倒だからモックを使うことがあるのではないか、と問い直した。

疑問は、モックを全面的に避けるべきかということより、何に依存すると変更に弱くなるのか、という点にあった。

## 2. 原稿化時の補足：実装を動かすことと、内部の手順を固定すること

本物の実装を動かすこと自体と、内部でどの関数を何回・どの順序で呼ぶかをテストの合否条件にすることは区別できる。

例えば、外部から見える結果が同じでも、内部の取得方法を変えると、呼び出し方を固定したテストだけが失敗する場合がある。モックによる相互作用の検証は、そのような結びつきを作りやすい。[1]

ただし、本物を使うテストでも内部状態や非公開メソッドを細かく検査すれば、実装の変更に弱くなる。反対に、代用品を使っていても結果を中心に確かめることはできる。

なお、会話では代用品を広く「モック」と呼んでいた。用語を細かく分ける場合、決めた値を返すスタブ、簡略化した実装を持つフェイク、呼び出しを記録するスパイなどもある。[1]

## 3. 仮例：同じ本のタイトルを、違う手順で取得する

以下は公開用に新しく作った、固定された小さな図書目録の例。実際の業務コードではない。大規模な目録を毎回全件取得する設計を勧める例でもない。

```javascript
const books = [{ id: "book-a", title: "架空の本" }];

function titleById(catalog, id) {
  return catalog.getById(id)?.title ?? "見つかりません";
}

function titleFromList(catalog, id) {
  return catalog.list().find(book => book.id === id)?.title
    ?? "見つかりません";
}

function makeCatalog() {
  const calls = [];
  return {
    calls,
    getById(id) {
      calls.push("getById");
      return books.find(book => book.id === id);
    },
    list() {
      calls.push("list");
      return books;
    },
  };
}

for (const lookup of [titleById, titleFromList]) {
  const catalog = makeCatalog();
  const title = lookup(catalog, "book-a");
  console.log({
    correctTitle: title === "架空の本",
    calledGetById: catalog.calls.includes("getById"),
  });
}
```

| 確かめること | `titleById` | `titleFromList` |
| --- | --- | --- |
| 求めたタイトルが返る | 成立 | 成立 |
| 内部で `getById` を呼ぶ | 成立 | 不成立 |

この代用品には呼び出しを記録するスパイの役割もある。`calledGetById` が真であることを必須条件にすると、結果が同じでも取得方法を変えただけでテストは失敗する。

一方、「外部への送信は一度だけ」のように呼び出し回数自体が要件なら、それを検証する意味がある。どの呼び出しも実装詳細として無視してよいわけではない。

## 4. 今回整理できることと、追加で検討する論点

DBの準備が重いという当時の疑問は、そのまま残る。代用品で特定の条件を作りやすくすることと、実DBのSQLや制約が正しく動くことを確認することは、別の検証目的になる。

今回の整理では、まず何を保証したいテストなのかを決め、そのうえで代用品を使う範囲と合否条件を選ぶ。本物かモックかという二択だけでは、変更に強いかどうかを判断しきれない。

今後の検討点としては、呼び出し回数が要件になる境界、実DBで確認する範囲、代用品の振る舞いが実物からずれることへの対処がある。これらは原稿化時に追加した論点で、当時解決済みだったとは扱わない。
